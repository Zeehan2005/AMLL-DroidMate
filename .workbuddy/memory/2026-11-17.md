# 2026-11-17 工作日志

## AMLL 组件在 App 内比网页版卡顿的归因分析（只读排查，未改代码）
- 主因：时间同步被设为「与屏幕刷新率同步」（`AMLLLyricsView.kt:141-143,401-405`），每帧走 MediaSession 轮询（`MediaInfoService.kt:73,447-449`）→ `NowPlayingMusic.timestamp`（`global/Lyrics.kt:23`）导致 StateFlow 每帧发射 → Compose 重组 → `evaluateJavascript` bridge。网页版由播放器时钟直接驱动 rAF，链路短得多。
- 次因 1：`frontend/src/main.tsx:221-232` 的 rAF `player.update(delta)` 与 `:294-317` `window.updateTime` 中 `p.update(0)` 并存，每帧至少两次全量更新。git `f4440d6` 曾移除后者（实测单次 30ms），但被 `e989172` 回退。
- 次因 2：bundle 内 `renderStyles` / `isInSight` 写样式后同步读 `clientHeight`（amll.bundle.js:24915/24844），强制布局抖动约 4ms/帧；历史补丁随回退一起消失，core 0.5.2 仍存在。
- 其他：blur/mask/plus-lighter/will-change 等逐帧 CSS 在 WebView 开销大；WebGL mesh 背景默认开启（`AMLLSettings.kt:357`，`AMLLLyricsView.kt:606-613`）与 DOM 歌词抢 GPU；无 UA 降级路径；每帧仍读 SharedPreferences、重建 JSON、排序字体列表（`AMLLLyricsView.kt:429,443,603-687`）。
- 验证顺序建议：DevTools 抓 updateTime 长任务 → 关背景+模糊做 A/B → 临时把刷新间隔改 100ms 对比（会复现 #81 换行延迟）。

## 已实施：对齐网页版的时钟驱动方式（同日晚些时候）
- 核心改造：**时间推进移入 WebView 内部 rAF + 本地时钟**，原生只做 ~5Hz 低频锚点校准。
  - `frontend/src/main.tsx`：新增 `playbackClock`、`getPlaybackTime()`、`resetPlaybackClock()`、`applyPlaybackState()`；tick 每帧按本地时钟 `setCurrentTime`（同一 ms 去重）+ 一次 `player.update(delta)`；`window.syncPlaybackTime` 校准（小幅误差 300ms 平滑、>=1500ms 视为 seek 硬重置、忽略未推进的重复原生采样）；`window.seekPlaybackTime` 用于立即跳转；`window.updateTime` 保留为兼容别名。
  - `AMLLLyricsView.kt`：移除按刷新率每帧 `evaluateJavascript`，改为 `TIME_ANCHOR_INTERVAL_MS=200L` 的锚点；播放状态变化立即同步；去掉无效的 `window.callPlayer` 调用；`window.__amll.clock` 暴露时钟便于 DevTools 验证。
  - `MediaInfoService.kt`：轮询从屏幕刷新率（8~16ms）改为固定 100ms，消除 StateFlow 每帧发射/Compose 重组风暴；#81 换行延迟由 JS 本地逐帧时钟解决，不再依赖高频轮询。
- 未恢复历史 `clientHeight` 补丁：当前 core 0.5.2 的 `isInSight` 已用 ResizeObserver 的 `lyricGroupSize` 缓存，仅 bg-first 双行歌词读 `bgWrapper.clientHeight`，补丁收益小且有陈旧布局风险。
- 验证：`npm run build` 成功；`java -jar gradle/wrapper/gradle-wrapper.jar :app:compileDebugKotlin --offline --no-daemon` BUILD SUCCESSFUL；产物已同步到 `app/src/main/assets/amll/`。尚未做真机运行时帧率实测。
