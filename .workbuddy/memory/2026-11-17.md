## AMLL 组件在 App 内比网页版卡顿的归因分析（只读排查，未改代码）
- 主因：时间同步被设为「与屏幕刷新率同步」（`AMLLLyricsView.kt:141-143,401-405`），每帧走 MediaSession 轮询（`MediaInfoService.kt:73,447-449`）→ `NowPlayingMusic.timestamp`（`global/Lyrics.kt:23`）导致 StateFlow 每帧发射 → Compose 重组 → `evaluateJavascript` bridge。网页版由播放器时钟直接驱动 rAF，链路短得多。
- 次因 1：`frontend/src/main.tsx:221-232` 的 rAF `player.update(delta)` 与 `:294-317` `window.updateTime` 中 `p.update(0)` 并存，每帧至少两次全量更新。git `f4440d6` 曾移除后者（实测单次 30ms），但被 `e989172` 回退。
- 次因 2：bundle 内 `renderStyles` / `isInSight` 写样式后同步读 `clientHeight`（amll.bundle.js:24915/24844），强制布局抖动约 4ms/帧；历史补丁随回退一起消失，core 0.5.2 仍存在。
- 其他：blur/mask/plus-lighter/will-change 等逐帧 CSS 在 WebView 开销大；WebGL mesh 背景默认开启（`AMLLSettings.kt:357`，`AMLLLyricsView.kt:606-613`）与 DOM 歌词抢 GPU；无 UA 降级路径；每帧仍读 SharedPreferences、重建 JSON、排序字体列表（`AMLLLyricsView.kt:429,443,603-687`）。
- 验证顺序建议：DevTools 抓 updateTime 长任务 → 关背景+模糊做 A/B → 临时把刷新间隔改 100ms 对比（会复现 #81 换行延迟）。

## 显隐动画时间与卡片完全同步（23:40，接上条）
- 关键发现：虽然两处 `AnimatedVisibility` 的 fade 时长与卡片同为 `controlsTransitionDuration=250ms`，但它的 `visible` 依赖 `controlsInLayout`（= `controlsVisible || controlsAlpha > 0.01f`），淡出要等卡片 alpha 走完才启动，实际时机错开、视觉不同步。

## 系统状态栏显隐：顶部内容不缩动（23:45）
- 需求：全屏隐藏系统状态栏时图标不显示，但顶部标题栏/提示区不因状态栏 inset 塌成 0 而往上跳，"显隐均在原位"。
- 根因：全屏分支顶部覆盖层用 `.statusBarsPadding()`，`hide(systemBars())` 后该 inset 变 0 → padding 塌缩。状态栏 hide/show 逻辑在 MainScreen.kt 约 948-990 行的 SideEffect（`keepChromeVisible` 决定）。
- 方案：MainScreen 顶部用 platform API 读取固定状态栏高度 `ViewCompat.getRootWindowInsets(view)?.getInsetsIgnoringVisibility(Type.statusBars())?.top`，`remember(density, view)` 转成 Dp；全屏两处顶部 Column 改用 `.padding(top = statusBarInsetTop)` 替代 `.statusBarsPadding()`。横屏普通模式（状态栏常驻）那处 statusBarsPadding 保留。
- 坑：Compose 的 `WindowInsets.statusBarsIgnoringVisibility` 虽在 foundation-layout 1.12.1 字节码里存在，但 Kotlin 前端（ABI jar）解析为 Unresolved，即便加 `@OptIn(ExperimentalLayoutApi::class)` 也不行 → 改用 platform API 规避。新增 import：LocalDensity、ViewCompat。
- 验证：`:app:compileDebugKotlin --offline` BUILD SUCCESSFUL。

## 新功能：从其他界面返回主界面时不自动隐藏（23:52）
- 需求：从设置/自选歌词等界面回到主界面后，控件+状态栏保持显示，直到用户有任意操作才恢复 3 秒自动隐藏。
- 实现（MainScreen.kt）：
  - 新增 `showControlsAndWaitForInteraction()`：cancel 计时 job、置 null、`controlsVisible=true`，但不启动新计时。各用户操作入口仍走 `resetHideTimer()`（会启动 3s 隐藏）。
  - 在 BackHandler 附近加 `DisposableEffect(mainLifecycleOwner)` + `LifecycleEventObserver`：`ON_PAUSE` 标记 `pausedByLeaving=true`；`ON_RESUME` 时若标记为真则清除并调用 `showControlsAndWaitForInteraction()`。用 ON_PAUSE→ON_RESUME 判定"返回"，避免首次进入（无前置 ON_PAUSE）误触发。
- import 坑：`LocalLifecycleOwner` 用新的 `androidx.lifecycle.compose.LocalLifecycleOwner`（旧的 `androidx.compose.ui.platform` 已 deprecated）；lifecycle-runtime-compose 由 lifecycle-viewmodel-compose 传递依赖，无需在 build.gradle 显式声明。
- 验证：`:app:compileDebugKotlin --offline` BUILD SUCCESSFUL，无警告。
- 补充（冷启动也常驻）：冷启动不触发 ON_PAUSE→ON_RESUME，且全屏分支原第 1038 行 `LaunchedEffect(Unit){resetHideTimer()}` 会主动启动 3s 隐藏 → 刚进 app 仍会藏。把该行改为 `showControlsAndWaitForInteraction()`，冷启动/重进全屏与「返回」统一为显示但不启动计时，直到用户操作。编译通过。
- 补充（菜单展开不隐藏）：`showMenu` 是三处 DropdownMenu 共享状态，展开时若 3s 计时到点会连菜单一起隐藏。加 `LaunchedEffect(showMenu)`：展开→`showControlsAndWaitForInteraction()`（取消计时常驻），收起→`resetHideTimer()`（恢复隐藏）；`menuHasBeenOpened` 首次标志避免冷启动 showMenu=false 误触发计时。编译通过。
